# OCC 肉鸽交互与基础架构开发计划 v0.1

> 状态：候选启动计划，尚未写入“唯一当前主任务”。  
> 日期：2026-08-05。  
> 产品决定：暂不扩充事件、技能、敌人或地区内容；继续优化现有完整切片的交互体验与基础架构。

## 1. 当前判断

首区内容已经足够承担系统和交互验证，下一轮不需要增加内容数量。当前更值得解决的是：正式 UI 的焦点、返回、确认、禁用原因和操作反馈不够统一；运行时 UI 存在多 Canvas、多套构建辅助函数、每帧轮询和整页重建；`CombatPrototypeBootstrap` 同时承担流程、存档、战斗装配、输入、绘制与开发工具职责，继续堆功能会快速增加回归风险。

本路线只调整交互合同与代码边界，不改变战斗数值、状态、奖励、地图拓扑、存档语义和无时间压力规则。

## 2. 推荐路线

### R-UXA1：正式 UI 交互状态、焦点与基础动效反馈（首批）

首个推荐任务。先让入口、地图、设置、档案、简报、战斗与结算拥有一致的操作规则，再进行更深的代码拆分。

目标：建立统一的页面/覆盖层状态、返回栈、默认焦点、焦点恢复、确认对话框、禁用原因与短时操作反馈；同时补齐按钮、焦点、页面和模态层的首批基础动效，让界面更灵动但仍保持清晰、克制和可随辅助设置减弱或关闭。支持鼠标、键盘和手柄式导航语义，但不重做页面构图和业务流程。

建议交付：

- 新增纯数据 `UiScreen`、`UiOverlay`、`UiNavigationState` 与 `UiActionFeedback` 合同。
- 正式入口、地图、设置、档案和简报统一使用显式页面/覆盖层状态，不再用局部布尔值和嵌套枚举各自猜测返回目标。
- 页面打开时选择第一个合理控件；关闭设置/档案/确认框后恢复之前的焦点。
- 建立统一“返回”动作：覆盖层优先关闭，简报返回地图，地图返回入口；战斗中返回不得暗中退出或改变状态。
- 为覆盖已有存档的新开推进、战术重开、离开未完成战斗等高影响操作提供正式确认框；确认框不使用开发控制台。
- 所有禁用按钮显示明确原因，例如“暂无存档”“零件不足”“节点不可达”“需先完成当前结算”。
- 成功、拒绝、保存完成等操作使用统一、短时、非阻塞反馈，不弹出强制等待层。
- `RuntimeUiEventSystem` 负责唯一事件系统与当前选择有效性，不重复创建输入模块。
- 新增共用 `UiMotionProfile`/动效令牌，统一即时、快速、标准三档时长与缓动；优先复用现有 DOTween，不引入多帧动画资产依赖。
- 按钮悬停、按下、选中和禁用使用边线、底色、亮度与 1–2px 位移等克制反馈；不持续缩放文字，不使用高频闪烁或铺满面板的高饱和冷青。
- 页面切换使用短距离位移与淡入，设置/档案/确认框使用遮罩淡入和轻微展开；默认总时长控制在约 0.12–0.28 秒，不能让玩家等待动画结束才能理解状态。
- 焦点轮廓可使用低频呼吸，但必须保持清晰静态边界；动画强度为 0 时立即进入最终状态，高对比模式下仍可辨认。
- 动效只消费交互/展示事件，不提交命令、不保存状态、不改变按钮可用性和玩法结算。

验收标准：

1. 入口、地图、设置、档案、简报、战斗 HUD 和结算均有明确默认焦点；鼠标点击后键盘/导航继续有效。
2. 设置、档案与确认框关闭后恢复原焦点；重复开关不会留下指向已销毁对象的 `currentSelectedGameObject`。
3. Escape/Cancel/返回按钮遵循同一返回栈；任何返回都不绕过奖励、存档或战斗结算。
4. 三类高影响操作至少覆盖：新开覆盖存档、战术重开、离开战斗；取消操作必须保持状态完全不变。
5. 所有不可用主操作均有可见原因；成本不足和节点不可达不会只表现为“按钮没反应”。
6. Funplay 真实点击与键盘模拟覆盖入口→地图→设置/档案→简报→战斗，以及确认/取消和焦点恢复。
7. 1920×1080 与真实 960×540 无确认框、反馈条或焦点轮廓溢出。
8. 按钮四态、页面进入/退出、模态打开/关闭和提示条均有稳定动效语义；动画强度 0%/100% 都能完成同一交互结果，0% 不残留透明或不可点击状态。
9. 同一控件快速重复输入不会叠加无限 Tween、重复提交命令或遗留被 Kill 的半完成状态；界面销毁时相关 Tween 正确清理。
10. R-F6 固定种子、永久安全回访、奖励防重复和存档恢复回归不变。
11. Funplay 编译错误/警告 0，Console 无新增项目错误；退出 Play Mode，场景 `isDirty=false`，不保存场景。

完成后解锁：R-UXV1 基础界面视觉反馈语义扩展。

### R-UXV1：基础界面视觉反馈语义扩展

目标：在 R-UXA1 的共用动效令牌上，为现有页面补充由真实状态变化驱动的轻量视觉反馈，不制作逐内容定制特效。

- 地图：节点选中、可达路径、当前位置变更和安全回访使用不同但稳定的边线/流向反馈；未知节点不通过动效泄露类型。
- 资源：零件、以太、补给、侦测与权限卡变化时突出发生变化的数字和方向；不让常驻资源栏持续闪动。
- 简报/确认：主要操作获得明确视觉主次；确认与取消的色彩、焦点和进入顺序一致。
- 战斗：行动选择、有效范围揭示、无效点击、目标确认和指令提交形成连续视觉链；复用既有 `CombatFeedbackEvent`，不重算结果。
- 结算：标题、摘要、三张奖励卡与领取结果使用短促分段进入和确认反馈；不延迟真实领取，也不允许重复提交。
- 所有效果在 960×540 下不遮挡文字、目标格、行动条或 HUD；屏幕震动只用于已批准的战斗反馈，不用于菜单和地图。
- 建立 `UiVisualEvent` 或同等只读表现入口，使视觉反馈不反向改写流程/战斗状态。

完成后解锁：R-UXA2 正式 UI 展示状态与事件驱动刷新。

### R-UXA2：正式 UI 展示状态与事件驱动刷新

目标：停止由各 UI 组件每帧拼接签名并整页销毁重建，将业务状态转换为只读展示模型，以显式变更事件刷新对应区域。

- 新增入口、地图、简报、战斗、结算所需的只读 presentation model。
- UI 不直接修改 `CombatState` 或 `RogueliteMapRun`；命令仍通过明确的协调入口提交。
- 用版本号/变更事件替代字符串签名轮询；只刷新改变的页面或卡片。
- 保持现有运行时生成 UI，不在本任务强制制作 Prefab 或保存场景。
- 建立刷新次数、活动对象数量和焦点稳定性测试，避免一项资源变化重建整页。

完成后解锁：R-UXA3 共用 UI 组件、主题、布局与动效令牌。

### R-UXA3：共用 UI 组件、主题、布局与动效令牌

目标：收束 `FormalRogueliteUi`、`FormalCombatHud` 与 `RogueliteSettlementPresentation` 重复的 Canvas、Label、Button、Panel、字号和颜色实现。

- 建立统一 Canvas 根、排序层、缩放策略和安全区域合同。
- 建立共用主题颜色、字号、间距、按钮状态、焦点轮廓、图标槽、动效时长与缓动令牌。
- 共用组件保持纯表现，不读取或改写玩法状态。
- 继续验证 1920×1080 与 960×540，禁止通过全局缩小字体掩盖布局问题。

完成后解锁：R-ARCH1 `CombatPrototypeBootstrap` 职责拆分。

### R-ARCH1：流程协调、存档网关与战场展示职责拆分

目标：在测试保护下逐步缩小 `CombatPrototypeBootstrap`，不一次性重写。

- 抽出肉鸽流程协调器：入口、地图、简报、战斗、结算状态转换。
- 抽出存档网关：PlayerPrefs 键、读取、兼容、保存和错误报告。
- 抽出战场展示/输入适配器：格子坐标、点击解析、选择预览和绘制所需只读数据。
- 将开发 IMGUI 与正式玩家流程明确隔离；开发工具只通过测试接口调用协调器。
- 每次只迁移一个职责，并保持已有公共入口的兼容薄封装，避免大爆炸式重构。

完成后解锁：R-UXB1 战斗操作预览与错误反馈收口。

### R-UXB1：战斗操作预览与错误反馈收口

目标：让移动、攻击、技能、搜刮、互动和结束行动在提交前后都清楚表达目标、成本、范围、结果与失败原因。

- 选中行动后显示目标规则、有效格、成本和预期确定性结果。
- 无效点击提供明确原因，不静默失败，也不弹阻塞窗口。
- 操作成功后统一恢复或保留选择状态，避免每类命令行为不同。
- 不改变命令解析、伤害公式、状态顺序或敌人 AI。

完成后解锁：R-UXR1 完整交互回归与架构基线冻结。

### R-UXR1：完整交互回归与架构基线冻结

- 鼠标、键盘/导航、确认/取消、焦点恢复、基础动效、动画强度 0%/100%、存档错误、战术重开与完整首区流程联合回归。
- 记录主要组件职责、依赖方向和可扩展入口。
- 通过后，后续内容策划可建立在稳定交互与架构上，但本路线本身不启动内容扩容。

## 3. 执行纪律

- 每轮只激活一个唯一当前主任务；推荐先执行包含首批基础动效的 R-UXA1。
- 先写交互状态合同和纯逻辑测试，再接运行时 UI，最后做 Funplay 真实输入验证。
- 不以制作新页面、Prefab 化、场景重搭或逐页定制动画替代交互/动效合同；未经明确要求不保存场景。
- 基础动效优先复用 DOTween、CanvasGroup、边线和现有静态像素资产；不引入未经 QA 的正式资产或多帧动画依赖。
- 不同时进行 `CombatPrototypeBootstrap` 大拆分和玩家交互改版；先固定行为，再移动职责。
- Unity 脚本/资产每次改动后都通过 Funplay 重编译、检查 Console 与场景脏状态。
- 不覆盖用户未提交改动，不触碰 `Library/`、`Logs/`、缓存、`Assets/_Recovery/`、Package 与 ProjectSettings 的既有改动。
