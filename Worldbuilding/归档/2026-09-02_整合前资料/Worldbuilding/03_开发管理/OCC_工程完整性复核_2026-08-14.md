## 当前工作区复核

### P1：万能入口继续膨胀

`CombatPrototypeBootstrap` 同时持有战斗与肉鸽状态、存档网关、输入状态、地图视口、敌方行动序列、资源加载、HUD/结算/启动页/背包/训练场引用，并直接绘制战场和处理命令。多个表现组件又以整个 Bootstrap 作为服务定位器，任何页面需求都能继续向入口加字段和方法。

处理原则：从现在起不再给该类新增职责。后续按以下接缝提取，不做一次性重写：

1. `CombatSessionController`：战斗状态、命令提交、回合与重开；不引用具体 HUD。
2. `RogueliteRunController`：地图选择、结算、存档；不引用战场绘制。
3. `BattlefieldInputController`：视口、指针、键盘目标与选择取消。
4. `CombatPresentationFacade`：只暴露 UI 需要的只读模型和命令接口，替代各 UI 对 Bootstrap 的整对象依赖。
5. Bootstrap 最终只负责组装组件和生命周期，不承载玩法规则或页面绘制。

每次只提取一个接缝，保持行为测试通过后再进入下一步。

### P1：未提交范围无法作为单一提交审查

当前改动至少包含学院 40 节点地图、战斗目标伤害预估、单位头顶信息、战斗反馈、全局 UI 主题与导航图标、周边页面、正式/样本美术和开发文档。禁止把它们压成一个“整理 UI/地图”的提交。

建议提交顺序：

1. 学院地图策划源文件、地图状态/拓扑、地图测试。
2. 伤害预估与单位 HUD 的纯模型、对应测试。
3. 战斗输入/反馈行为与对应测试。
4. UI 主题、布局合同、导航/语义图标、导入审计。
5. 各正式页面接线；Bootstrap 只接受必要接线，随后立即开始提取 facade。
6. 美术原料、QA 产物与 Unity 正式资产分别提交，不混用“样本”和“正式”身份。
7. 最后提交待办、开发计划和验证记录。

每批提交都必须在暂存前用 `git diff --cached --stat` 检查是否跨越上述边界。

### P1：决策源与流水账混在一起

`OCC_当前待办.md` 已超过 900 行，既有当前主任务、最近完成、暂停项、旧开发顺序、验证表，也保留部分历史乱码。它不再适合作为长期决策库。

处理原则：

- 当前待办只保留一个当前任务、最多 10 个最近完成项，以及指向归档/验证记录的链接。
- 玩法决定写入 `Worldbuilding/01_游戏策划/` 对应源文件；美术决定写入美术规范；技术边界写入开发管理下的决策记录。
- 待办只引用决策 ID 和验收证据，不复制整段规则。
- 历史区另行归档时修复乱码；本轮不批量重写，以免覆盖来源不明的用户修改。

### P2：存档格式维护成本上升

`RogueliteMapRun.ToJson/FromJson` 使用带位置含义的 `map10` 管道字符串，目前已有多代兼容分支。现有验证网关降低了损坏风险，但每新增字段都需要同步长度、索引、旧版布局与测试，容易出现“能解析但语义错位”。

下一次存档字段变化前先建立命名 DTO 和版本迁移器；不要再发布 `map11` 位置字段。旧版本只读迁移，当前版本统一写命名结构，并保留写后读与语义验证。

### P2：显示词汇仍有重复来源

状态名称分别存在于 `CombatResolver`、`CombatPrototypeBootstrap` 和 `TacticalHudSceneBinder`；肉鸽节点/奖励/术式名称也有页面私有映射。短期不会编译失败，但新增状态或改名可能让日志、HUD 和详情页不一致。

处理原则：运行时只暴露稳定语义 ID；中文显示名集中在只读 Presentation Catalog。玩法计算不得依赖显示文字。
