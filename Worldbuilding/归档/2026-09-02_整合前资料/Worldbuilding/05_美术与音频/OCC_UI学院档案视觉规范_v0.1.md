# OCC UI 学院档案视觉规范 v0.1

**状态：ACTIVE / SUBORDINATE（2026-08-23）。** 适用于启动、入口、地图、简报、整备、设置、档案、结算与战斗 HUD；不改变任何玩法信息层级或交互合同。本文件只细化学院档案UI主题，资产尺寸、来源、通用颜色语义与状态晋级服从 `OCC_美术规范_v0.1.md` 唯一合同。

## 1. 角色与玩家阅读

- **资产角色：** 剧情／肉鸽共用的运行时 UI 主题、公共皮肤与页面背景。
- **一秒阅读目标：** 玩家先读出当前页面、主要行动和危险状态，再读资源与说明；界面应像学院发放的行动档案和实地调查夹，而不是军事终端或未来控制台。
- **叙事／材质前提：** 近代魔法工业文明；信息载体来自暖纸、硬纸卡、布面档案夹、搪瓷标牌、炭墨和少量氧化黄铜。以太是可测量、可维护的能源，只在真实激活处出现冷青。

## 2. 形状、明度与密度

- 公共容器使用水平纸卡、窄标签条、登记线和稳定直角；允许极少量裁切角，不使用装甲斜切、六边形蜂巢、霓虹框或管线边框。
- 页面以浅色纸面为最大明度面积，炭墨文字和边界承担结构；深色只用于页脊、遮罩、战斗指令底座和危险封条，不得重新铺满整屏。
- 每个模块只保留一个标题、一个主体信息区和至多一个语义强调。装饰不得与文字、图标、资源条竞争。
- 常规页面不使用扫描线、滚动网格、示波器条纹、系统接入动画或持续发光边缘。

## 4. 页面不变量

- **启动：** 使用“学院行动档案／实地调查卷宗”叙事，不出现 `OPERATIONS CONTROL`、链路同步、操作员接入等终端话术。
- **入口／地图／简报／整备：** 共享纸面、档案卡、页脊和登记标记；地图本体可保留独立地理色，但外围 UI 必须服从本规范。
- **战斗 HUD：** 底栏以上保持 75% 战场／25% HUD 信息结构；底部指令托盘横跨完整参考画布，在 16px 外边距内使用 1888px 宽度。顶部页签、右侧记录夹和底部指令托盘可使用少量深炭墨承重，但卡片与文字阅读面以暖浅色为主。
- **高对比模式：** 纸面趋近白，炭墨趋近黑；不得恢复蓝黑底。

## 5. 排除项

- 排除蓝黑整屏、冰蓝描边、扫描线、终端网格、玻璃全息、HUD 雷达、示波器、未来舰桥和赛博霓虹。
- 排除中世纪羊皮卷卷边、蜡封滥用、哥特花纹、法阵装饰和神圣金光。
- 排除齿轮、铆钉、铜管堆叠的纯蒸汽朋克，以及圆润玩具按钮、柔焦、玻璃拟态和大面积渐变。

## 6. 目标尺寸验收

- `1920×1080` 与 `960×540` 都能先读页面标题、主要行动、生命／魔力／风险和当前节点。
- 正式文字使用仓库内可追溯的真实中文字体。短标签、按钮、菜单、模式提示和数值统一使用 `FusionPixel12ProportionalZhHans`，严格按 12px 母版的 `2×／4×／6×` 层级呈现：正文／交互为 `24`，页面标题为 `48`，强反馈为 `72`；不再允许 16／18／20／22／26／28／36 等任意中间字号。24px 单行槽至少 `40px`，两行至少 `72px`，48px 标题槽至少 `72px`；Pixel Perfect、整数位置、Normal 字形、禁用 Best Fit、合成粗体、斜体、文字阴影与多重描边。超过两行的日志／档案正文可切换为明确的清晰黑体阅读角色，但同一句、同一按钮和同一数值行内不得混排。
- 正文对主纸面／档案卡对比度至少 `7:1`；次级文字至少 `4.5:1`。
- 两种分辨率下不出现蓝黑整屏回读、扫描线、冷青普通边框或纸面文字对比不足。
- 选中、危险、交互、恢复和禁用不能只靠颜色区分，仍须保留形态、图标或文字状态。

## 7. 像素框架合同

- 这里的像素风格来自明确的方格尺寸、阶梯方角和离散位移，不来自低分辨率模糊、抖动或锯齿化文字。字体、地图和插画仍保持清晰。
- 已登记的 `FormalUISkin16` 是面板、按钮、页签、槽位、资源条和焦点框的正式运行时边框来源；浅纸面继续承担阅读底色，皮肤 Sprite 以不拦截射线的九宫格边框层覆盖在控件上，使用已登记的 `4px` border 且关闭不透明深色中心，不得以运行时矩形框冒充正式皮肤。按钮的普通、悬停、按下、禁用与选中状态必须切换对应状态皮肤。
- Canvas 的 `referencePixelsPerUnit` 必须与 `32 PPU × 4 倍逻辑像素` 对齐；`16/32/64/128px` 图像族只允许按原生尺寸的整数倍显示。禁止 `16→42`、`32→22`、`32→54.4`、`128×32→307.2×76.8` 等非整数缩放。
- 主要卡片、按钮、弹窗、槽位和提示框使用 `6` 参考像素外框；四角使用 `12×12` 参考像素方块或等价阶梯缺口；允许在上／左内侧增加 `2` 参考像素纸面高光。
- **文字边框安全区：** 字形可见包围盒与 `6px` 外框的内缘之间，四向至少再保留 `6px` 参考安全距；因此承载 `24px` 单行文字的完整独立外框高度不得低于 `48px`。高度不足时必须只保留上级模块外框，内部行改用无外框浅底、状态侧条或 `2px` 底部分隔线；禁止给每一行重复套重框后让深色边界穿过字形。
- **右键菜单双行合同：** 动作名与资源说明必须使用两条独立字形基线，完整按钮行高不得低于 `76px`；动作名字形顶部和资源说明字形底部都必须满足 `12px` 完整框安全内缩，两行可见字形之间至少留 `4px`，不得用两个各 `40px` 的文字槽直接塞进 `76px` 行后让第二行进入底框。
- **战斗底栏比例与术式卡合同：** 全宽指令托盘参考尺寸为 `1888×200px`，五组横向宽度依次为移动／武器 `200px`、个人术式 `1100px`、交互 `152px`、战术栏 `176px`、结束回合 `204px`，组间保留 8px 间距。八个快捷术式采用 `4×2` 横向卡阵列，单卡参考尺寸 `268×76px`，内部严格服从玩家批准草图：左侧 32px 正式术式图标以整数 2× 显示为 `64×64px`，`24×24px` 黑色快捷键块叠在图标左上角；中部只放 `122×40px` 居中术式名，常驻名称最多五字，超出后省略并由悬浮详情显示全名；右侧为单一 `60×64px` 深冷炭墨资源块，上下两行各使用 `56×32px`，分别承载行动点与个人魔力原生 16px 图标的严格整数 2× `32×32px` 显示及消耗值，已装备术式的零消耗必须显示 0。资源区禁止中性灰底、白色／浅色数值底框、横向底部费用带和分散小卡，只允许统一深冷炭墨块上的反白数字；空槽使用更暗的冷调炭墨，不得改用 `Muted` 灰。术式卡本体禁止继续渲染带灰色承重下沿的标准按钮九宫格皮肤，但四边必须使用独立 `2px` 炭墨直线细框，在 960×540 下对应 1 个物理像素；悬停／按下／选中／禁用由平面底色、细框／焦点框、资源块与文字状态表达。对应资源不足时仅将该数字和深冷底色语义染色。冷却／风险状态章位于名称区右侧，不得覆盖资源块。空间不足时不得缩字、隐藏费用或改变三块顺序。背包入口固定在顶部抬头，只保留“背包 [B]”。
- **战斗资源条合同：** 英雄生命、护盾和个人魔力轨道参考高度不得低于 `24px`，轨道必须显示 25%／50%／75% 刻度；正式像素轨道皮肤位于底层，语义填充四边内缩 `4px` 后位于皮肤上层，禁止旧的彩色九宫格中心或厚边遮住填充。生命使用锈红、护盾使用灰绿、个人魔力使用冷青，三者不得都读成黑条。有固定上限的资源同时显示当前值、上限和整数百分比，无上限护盾明确标记“无上限”。数值变化除宽度过渡外，必须在新比例落点显示一次不漂移的增减色闪标；关闭动效时仍立即更新宽度和读数。
- **战场单位条合同：** 单位脚下生命／护盾轨道在 128px 参考格分别为 `120×22px` 与 `120×14px`，四边内缩 `2px` 使用锈红／灰绿纯色填充，轨道为浅中性档案灰；禁止把 `bar_segment_health/shield` 彩框继续叠在小尺寸填充上。两条都显示四分位刻度，变化必须具备比例宽度过渡、填充闪烁和新比例落点闪标；在缩放后仍必须先读出颜色比例，而不是黑色外框。
- **敌人意图图标合同：** 原生 `16×16px` 意图图标在单位头顶只能按整数 `2×` 显示为 `32×32px`，置于 `40px` 高徽章内四向居中；徽章顶部相对单位逻辑格使用 `-22px` 参考偏移，使徽章下沿停在头像透明净空内而不压住头部。不得以 1× 偏在左上角，也不得做非整数拉伸。移动意图使用已批准的双箭头移动符号，禁止继续使用会被误读成“!!”的旧足迹像素。
- 在 `960×540`（参考画布的 0.5 倍）下，上述尺寸分别落为至少 `3`、`6×6`、`1` 个物理像素，禁止再使用单个参考像素作为主要容器边界。
- 分隔线可使用 `2` 参考像素，但不得承担主要容器轮廓；常规边界使用炭墨／登记灰，只有焦点、可执行、危险等真实状态可以切换为语义色。
- 按钮按下时使用 `4` 参考像素离散偏移；焦点与选中使用双层或角块加重，不使用柔光、圆角、亚像素位移或连续缩放。
- 大面积重复区域可以共用一个外框与内部网格，不为每个背景单元重复堆叠装饰；像素角块不得侵占标题、图标、路线、状态或点击净空。
- 入口、地图、简报、整备、设置、档案、结算、战斗 HUD、悬浮提示和战斗背包必须共享该合同。IMGUI 与 UGUI 的轮廓尺寸和状态语义必须一致。

## 8. 表面与文字配对合同

- **玩家阅读目标：** 任何承载正文、数值或状态说明的控件，在一秒内先读出文字；材质与像素装饰不得先于信息。
- 暖纸白、主纸面、档案卡、交互纸卡和浅色槽位一律使用炭墨正文；正文对实际底色至少 `7:1`，次级墨至少 `4.5:1`。
- 深炭墨只允许用于整屏遮罩、页脊、少量承重托盘、纯图标凹槽或明确的反字标签；一旦承载文字，必须使用暖白 `OnInk`，不得继承默认炭墨。
- 背包装备槽、网格槽、查询结果、战利品行和快捷栏属于阅读表面，统一使用浅档案卡；选中状态通过以太青边框／侧条表达，不把整块恢复为蓝黑底。
- 禁用状态通过低对比暖灰底、图标或状态文案表达；禁止以近黑底叠加灰黑字模拟不可用。
- 悬浮说明和战斗结算属于阅读卡，必须使用抬升纸面；悬浮说明背景 alpha 至少 `.98`，地图道路、节点、建筑和分区线不得透进正文区。只有危险确认等确有必要的深底弹层才允许暖白反字。

## 9. 说明卡尺寸与玩家文案合同

- 说明卡按当前标题与正文自适应宽高，不得让一句短说明占用固定大卡；参考画布宽度范围为 `220–480`，高度范围为 `92–360`，到达上限后换行或截断。
- 短说明优先保持单行正文和紧凑留白；长说明只保留玩家作决定需要的消耗、目标、效果、风险与结果，不复制当前控件已经显示的名称或状态。
- 说明标题回答“这是什么”，正文回答“会发生什么／需要什么”；删除“地图节点状态”等同义复述，以及无操作价值的流程自述。
- 玩家可见说明禁止出现 `DefinitionId`、实例 ID、`AFF-*`、枚举名、运行时、状态机、验证器、合同、调试入口等开发术语。内容目录中的稳定 ID 必须先转换为正式显示名。
- 事件记录型说明只显示最近且与当前决策有关的条目，不得把整个运行日志塞入悬浮卡；完整历史应由独立可滚动页面承担。

## 10. 战斗 HUD 文字与数值合同

- **一秒阅读顺序：** 当前行动者／AP → 英雄生命、护盾、个人魔力 → 所选行动／目标 → 指令按钮 → 行动序列与最近记录。不得用日志或长效果说明抢占前三层。
- 当前行动卡最多保留两行决策正文：第一行是行动与可执行状态，第二行是目标和必要的最终生命伤害；完整预计过程、随机性说明与伤害拆分进入悬浮详情。
- 英雄资源采用左侧名称、右侧数值的固定分栏；名称与数值统一使用 `24px` 正文层，数值右对齐且不能随位数变化移动基线。肉鸽护盾显示“无上限”，不得恢复旧最大值。
- 行动序列、状态／生命摘要和按钮内消耗统一使用 `24px` 正文层；若空间不足，先减少常驻字数、转移到悬浮详情或扩大槽位，禁止缩小字号、合成粗体或裁掉上下缘。
- 行动序列使用“模块外框＋无外框浅底行＋底部分隔线”的层级；单行字形距分隔线至少 `6px`，不得把每个 `40px` 行重新包进 `6px` 重框。
- 单位头顶生命／护盾位于深色或语义色条上时必须使用暖白反字；生命与护盾保持独立行，不能让建筑、角色立绘、意图标记或状态图标遮住读数。
- 现场记录只常驻最近两条玩家可理解的结果；来源实例 ID、内容 ID、冒号式内部键和开发术语必须在进入 HUD 前转换或删除。

## 11. 玩家语言合同

- **先给玩家要做的事：** 信息顺序固定为“去哪里、做什么、会遇到谁、赢了得到什么、输了失去什么”。标题说明当前位置或结果，正文第一句先说会发生什么，最后再给下一步；不解释界面流程和系统结构。
- **使用学院里的人会说的话：** 正式界面应像教员、医务室职员、工坊师傅或同行学生在和玩家说话。世界观名词必须落在可理解的日常句子里；不把策划表、测试报告或数值说明书换个标题后直接展示。
- **按钮直接行动：** 使用“开始新游戏、继续游戏、行程与行囊、出发、先不去、结束回合、挑一件带走、回到地图”等清楚动作；不用“新开推进、提交指令、进入流程、执行操作、进入节点”等抽象说法。
- **提示必须可行动：** 禁用和失败提示至少包含“为什么不能”与“怎样才能继续”。例如“个人魔力不足：需要 4，当前 2”，而不是“当前指令不可执行”或“没有合法目标”。
- **正式界面不得留开发证据：** 禁止显示版本号、schema、构建号、种子、内容 ID、实例 ID、枚举名、内部键、池、档位、变体、固定／随机／确定性、迁移、快照、测试、验证、步骤数。需要排错的内容只进日志和开发控制台，不得伪装成世界观文本。
- **使用玩家术语：** 统一使用“学期进度、用时、行动点、回来时恢复、终考、记录、行囊、术式册”；禁止出现“持久化、执行适配、状态机、运行时、当前推进、Definition、AP 作废、合法空位”等实现术语或无解释缩写。
- **数字带对象：** 不能只写“+2 → 21”；应写成“用时 2 · 归来后 21”或在紧凑指标中用标题明确对象。资源不足同时显示“需要值／当前值”。
- **危险说清结果：** 不用“风险阈值、空间风险、失败档、成功奖励”等策划表标题。改用“难度、场地、如果输了、赢了可得”，并明确时间、生命、道具与奖励分别怎样变化。
- **短而完整：** 常驻正文尽量一至两句，每句只承担一个决定；悬浮说明不复述按钮名，不写“本页已……”“该系统将……”等界面自述。
- **系统界面保持诚实：** 存档、设置与输入提示可以使用必要的界面语言，但必须直白；不能把存储错误编成世界观事故，也不能暴露备份路径、校验结果或内部状态。
- **成功提示确认落点：** “已经带走”后说明奖励去了行囊还是术式册；“旅程已经记下”后说明下一步可以去哪里。禁止只说内部事件已提交或数据已写入。
