# OCC 战斗可读性与存档完整性联合开发计划 v0.1

> 日期：2026-08-09
> 交付顺序：`COMBAT-CLARITY-01` → `SAVE-INTEGRITY-01`
> 归属：剧情模式与肉鸽模式共用的战斗呈现、失败结算与地图运行存档基础设施

## 1. 总目标

先解决战斗过程“看不懂正在发生什么”的核心体验问题，再完成 `map9` 语义校验和坏档写保护。两项在同一开发任务中连续交付，但待办状态始终只保留一个当前主任务：`COMBAT-CLARITY-01` 完成并记录验证后，才把 `SAVE-INTEGRITY-01` 切换为当前进行。

本轮不改变敌人实际数值、AI 决策、技能效果、剧情探索规则或 `map9` 字段顺序；只让现有规则可见、反馈可信，并阻止语义无效存档被读取或覆盖。

## 2. 已确认问题

### 2.1 战斗可读性

- `FormalCombatHud` 把阶段、行动单位和 AP 混在一个短文本中，玩家无法快速区分“等待敌方”“选择指令”“选择目标”“结果结算”。
- 当前操作与结果预览共用一块短文本，目标规则、消耗、合法性、命中结果和失败原因没有稳定层级。
- 目标信息只显示生命、护盾和护甲；缺少最大值、格挡、速度、魔力、武器、技能、冷却与状态详情。
- 棋盘上敌人意图由 `GetEnemyIntent` 简化为“火术/攻击/靠近”，没有复用真实 `EnemyTactics.Choose`，可能与实际行动不一致，也不显示目标、技能名、伤害或状态。
- `CombatVisualFeedback` 已有浮字和命中特效，但显式效果发布与状态差值轮询可能重复产生反馈；护盾吸收、生命伤害、减伤来源和状态结果不够容易区分。
- 现场记录只显示最新一条，行动前因、行动结果和连续伤害很难追溯。
- 失败覆盖层只有“行动中止”和通用说明；没有失败原因、剩余敌人、目标状态、存档后果，也没有按剧情/肉鸽/独立战斗给出正确返回路径。

### 2.2 存档完整性

- `RogueliteSaveGateway` 能捕获解析异常并备份原文，但 `RogueliteMapRun.FromJson` 成功不代表状态在语义上合法。
- 当前写保护只保存在单个 Gateway 实例的内存集合中；重新创建 Gateway 后可能失去保护。
- 保存前没有统一验证节点、资源、生命、武器、术式、背包实例和快捷栏引用的不变量。
- 保存成功只代表存储调用没有抛异常，没有进行可靠的原文回读与语义复核。
- 错误状态对 UI 的信息不足，容易被误解为“没有存档”并触发覆盖流程。

## 3. 冻结决策

1. 战斗信息只从运行时权威状态和确定性预览生成，不在 HUD 内复制 AI、伤害或合法性规则。
2. 敌人意图必须由 `EnemyTactics.Choose(state, enemy, hero)` 的同一决策结果转换为只读展示模型；HUD 不再使用独立启发式猜测。
3. 选中敌人时展示完整战斗档案；所有存活敌人在棋盘或行动序列中至少显示一条紧凑意图摘要。
4. 当前阶段固定拆为：战斗开始、玩家选择指令、玩家选择目标、敌方行动、胜利、失败；不虚构没有权威数据支持的回合编号。
5. 操作预览固定分为：操作、目标规则、消耗、合法性、预计结果、风险/失败原因；伤害预览显示护盾吸收、生命伤害以及掩体/护甲/格挡减伤。
6. 战斗结果反馈以 `CombatEffectExecution` 为唯一主动事件源；状态轮询只作为未走执行器路径的兜底，并通过事件签名去重。
7. 失败不会静默把英雄死亡后的战斗状态覆盖为可继续地图存档。战术重开恢复本场开始快照；返回地图保留战前地图状态和当前节点；独立/剧情入口按原流程返回。除非后续产品决定，不新增永久死亡或自动删档。
8. `map9` 格式和版本号保持不变；新增的是解析后的语义验证、持久写锁、备份和回读验证。
9. 语义无效与文本解析失败都必须保留原始主槽、建立不可覆盖的首份坏档备份并设置持久写锁；只有用户明确确认的删槽操作可解除锁，备份继续保留。
10. 不保存或直接编辑 `.unity` 场景；优先新增只读模型和调整运行时 HUD/反馈脚本。未获明确授权前不进入 Play Mode。

## 4. 任务一：COMBAT-CLARITY-01

### 4.1 目标

让玩家在任意战斗时刻能够回答五个问题：现在是谁行动、我正在做什么、目标是谁、预计会发生什么、刚才实际发生了什么；失败时能够理解原因和下一步后果。

### 4.2 推荐结构

- 新增只读 `CombatPhasePresentationModel`：阶段标题、当前行动者、玩家可否输入、引导文字。
- 新增只读 `EnemyDossierPresentationModel`：生命/护盾最大值、护甲、格挡、速度、魔力、武器和两项技能详情。
- 新增只读 `EnemyIntentPresentationModel`：敌人 ID、命令类型、技能/武器名、目标、消耗、预计伤害/状态、是否需要移动。
- 扩展 `CombatActionPreview` 或新增结果分解模型，避免 UI 解析描述字符串。
- 新增 `CombatOutcomePresentationModel`：胜负、原因、目标状态、英雄终局状态、存活敌人、最近关键事件、重开/返回语义。
- 由 `CombatPrototypeBootstrap` 只负责协调模型和提交命令；格式化集中到模型/适配器，避免继续扩大 OnGUI/HUD 分支。

### 4.3 实施阶段

#### A. 先写失败回归

- 真实敌人决策与意图模型逐字段一致，包括武器攻击、技能、修补友军和移动。
- 选中敌人档案覆盖所有现有敌人原型、技能和冷却。
- 玩家操作预览覆盖合法/非法攻击、术式、卷轴和法宝，验证伤害分解与失败原因。
- 同一伤害执行只产生一组浮字/命中特效，不重复发布。
- 胜利、失败、战术重开和返回路径生成不同且正确的结算模型。

#### B. 阶段、当前操作与预览

- 顶部增加稳定阶段条：阶段名、当前行动者、AP、输入状态。
- 当前操作卡单独显示选中指令、技能/物品名、消耗和目标规则。
- 结果预览卡使用“合法/不可提交”明确状态，显示目标前后值、伤害分解、状态、范围格数和友军风险。
- 非法操作保留状态，不扣 AP、不改变目标；失败原因在按钮和预览卡同时可读。

#### C. 敌人信息与意图

- 点击敌人后，右侧档案显示完整数值、武器、技能、射程、伤害、消耗、冷却和状态。
- 每个存活敌人显示紧凑意图：行动图标/名称、目标与关键结果；选中敌人显示详细意图。
- 敌人执行前后使用同一意图签名验证实际命令；状态改变导致计划变化时立即刷新。
- 移除旧 `GetEnemyIntent` 启发式入口。

#### D. 伤害与行动结果反馈

- 生命伤害、护盾吸收、治疗、护盾恢复、状态和击倒使用不同语义颜色与短标签。
- 浮字锚定目标格，避免越过 HUD；连续结果按序错位，不能互相完全覆盖。
- 行动结果摘要显示攻击者、技能、目标、护盾变化、生命变化、减伤和状态结果。
- 现场记录扩展为最近 4–6 条，最新一条高亮；保留完整 `EventLog` 数据，不增加战斗日志第二数据源。

#### E. 失败结算

- 显示明确失败标题和原因：英雄倒下、目标失败或调试强制失败。
- 显示英雄终局生命/护盾、剩余敌人数、目标状态和最近关键事件。
- “战术重开”明确恢复本场开始快照；“返回地图/入口”明确哪些战斗内变化不会写入。
- 肉鸽失败不调用 `CaptureCombatInventory` 覆盖战前地图存档；胜利仍按现有流程捕获与结算。
- 所有离开、重开和可能替换存档的操作继续走确认层。

### 4.5 验收标准

- 任一存活敌人的完整数值、武器、技能和当前意图均可读取，意图与下一条真实 AI 命令一致。
- 玩家操作和结果预览分区明确，合法/非法、消耗、目标、伤害分解、状态与风险可在提交前读取。
- 每次实际伤害只显示一次，护盾与生命变化可区分；最近 4–6 条行动可追溯。
- 失败结算能说明原因、状态和返回后果；肉鸽失败不覆盖战前存档，战术重开恢复确定性快照。
- 1920×1080 继续保持 75% 战场 / 25% HUD；960×540 无关键文本裁切。视觉检查需先获得 Play Mode 授权。

## 5. 任务二：SAVE-INTEGRITY-01

### 5.1 目标

把“能解析”提升为“语义合法且可安全覆盖”，防止无效 `map9` 状态被继续加载、自动覆盖或伪装成缺失存档。

### 5.2 语义不变量

- 地图节点：当前、已访问、已完成节点均存在；当前节点与待结算/待战斗状态一致。
- 资源：等级、经验、通行卡、补给、侦察、零件、以太均非负且满足已冻结范围。
- 战斗状态：生命、护盾、魔力在合法上下界；战斗快照标记与当前节点类型一致。
- 构筑：武器、开局模板、已拥有/已装备术式 ID 有效；装备术式属于已拥有集合并满足武器相容规则。
- 奖励与选择：已领取奖励、待处理内容选择和待战斗任务相互一致，不含未知或重复引用。
- 背包：实例 ID 唯一、定义存在、剩余次数合法、摆放不越界不重叠、获取顺序与下一序列一致。
- 快捷栏：八格长度、引用实例存在、同一实例最多一格、可快捷装备、卷轴与法宝合计不超过四件。
- 序列化：`FromJson → Validate → ToJson → FromJson → Validate` 结果确定且不改变文本语义。

### 5.3 写保护流程

1. 读取原文并解析。
2. 执行语义验证；失败状态区分 `CorruptData`、`InvalidSemantics` 与 `StoreError`。
3. 首次失败时保存不可覆盖的原始备份，并写入持久锁标记；主槽原文保持不变。
4. 所有 Gateway 实例保存前检查持久锁，而非只依赖内存集合。
5. 新状态保存前先序列化、重新解析并通过语义验证；写入后回读原文并再次验证。
6. 任一步失败都返回明确错误，不把失败伪装为成功，也不自动新开覆盖。
7. 只有显式删槽确认清除主槽和锁；坏档备份继续保留供诊断。

- `Tests/EditMode/RogueliteSaveGatewayTests.cs`

### 5.5 验收标准

- 每类语义不变量至少有一个篡改字段的失败测试，且原始主槽不变、首份备份不变、持久锁存在。
- 新建 Gateway 后仍拒绝覆盖已锁坏档；显式删槽后可保存新局，备份仍保留。
- 保存前无效对象不会触碰存储；保存后回读不一致会返回失败并禁止继续覆盖。
- 旧 `map1–map8` 合法存档仍能迁移到合法 `map9`；合法 `map9` 往返文本确定。
- UI 明确区分“无存档”“坏档已保护”“存储故障”，不会自动覆盖。

## 6. 联合验证矩阵

1. 聚焦测试：战斗信息模型、敌人意图、伤害反馈、失败结算、存档语义与写保护。
2. 全量 EditMode；现有基线为 266/266，新增测试后必须全通过。
3. Funplay `request_recompile → wait_for_compilation → get_compilation_errors`，错误/警告为 0。
4. Funplay Console 无项目 error；活动场景 `isDirty=false`；Git 无 `.unity` 改动。
5. 未获授权前不进入 Play Mode；获得授权后补 1920×1080、960×540 的实际战斗信息与失败结算截图回归。
